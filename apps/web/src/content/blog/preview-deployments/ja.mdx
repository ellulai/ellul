プレビュー・デプロイメントとは、コードブランチに対するライブな URL のことです。差分ではなく、動いているアプリそのものです。この習慣は少なくとも2017年から存在し、コードを書くこととコードを読むことのギャップが広がるにつれ、毎年静かに重要さを増してきました。2026年、AI エージェントがコードを書くことが多くなった今、プレビュー URL は差分よりも多くのレビューを担うようになっています。

この記事は、その変化が重要な理由、プレビュー・デプロイメントが取る3つのアーキテクチャ形、そしてそれぞれの形が役に立つ場面を扱います。

## エージェントが出荷するときに、なぜプレビューがより重要になるのか

人間がコードを書くとき、人間は自分が何をしたかを知っています。どのファイルをなぜ変えたかを覚えています。差分は、自分の記憶を呼び戻すための記録です。レビュアーが差分を読むのは、人間の作者が向かいに座っているからです。

エージェントがコードを書くとき、PR を読む人間はレビュアーで、しばしば唯一のレビュアーで、差分を冷たい状態で読みます。差分は必要ですが、ライブ URL に比べて消費が遅いです。URL は5秒で「機能が動く」と告げます。差分は「217行から453行を見て、機能が動くことを確認してください」と15分かけて告げます。

もう少し微妙な問題があります。2026年のエージェントは自信があります。修正していようがいまいが、コミットメッセージに `// fixed the timezone bug` と書きます。テストがリグレッションをカバーしていようがいまいが、テスト合格と印を付けます。PR の中の文章は信頼できる要約ではありません。デプロイされたブランチの振る舞いは信頼できる要約です。プレビュー URL はエージェントの PR を信頼するための一部であって、装飾オプションではありません。

## 3つの形

### 形1:PRごとのエフェメラル(Vercel、Netlify、Render)

PR ごとに新しいビルドがトリガーされます。プラットフォームが固有のサブドメインにデプロイします。プレビューは PR が閉じるまで存続します。新しいコミットが入ると、プラットフォームは再ビルドしてデプロイを置き換えます。

**強み。** プレビュー間のクリーンな隔離。トラフィックが少なければ安価。広く理解されています。

**弱み。** ビルドごとのコールドスタート遅延。エージェントがビルド完了より速くコミットすると、プレビューは古くなる。永続的な状態がないので、プレビューでエージェントがデータベースに対して行ったことは、ビルドが回ると失われる。数分おきに反復するエージェントには合わない。

### 形2:エッジランタイム(Cloudflare Workers、Pages)

形1の派生で、デプロイ先がエッジランタイムです。各 PR が Workers のプレビュー環境にシップされ、数秒で世界に伝播します。

**強み。** 1桁ミリ秒のコールドスタート。グローバル伝播。スケールしても安価。

**弱み。** Workers のプログラミングモデルはランタイム以上に制約です。長時間接続、大きなインメモリ・キャッシュ、特定の Node API は再形成が必要です。スタックがすでに Workers をターゲットにしているなら見えませんが、スタックが Node をターゲットにしているなら、プレビュー環境は本番と異なります。

### 形3:永続ランタイム(ワークステーション自体)

エージェントのワークステーションがプレビューを提供します。PR ごとのビルドはありません。エージェントがワークステーション上で `pnpm dev`(または同等)を実行し、プレビュー URL はその長寿命プロセスを指します。エージェントがファイルを編集すると、次のページ読み込みでプレビューに反映されます。エージェントがローカルで作業していて、あなたがその開発サーバーを見ているのと同じです。

**強み。** ゼロ・コールドスタート。状態が反復間で残る。プレビューは、エージェントが今この瞬間に走らせているまさにそれです。「エージェントが動くと言う、人間が動くと確認する」を5分のループから5秒のループにします。

**弱み。** コストは PR 数ではなくワークステーション数でスケール。状態の永続性は両刃の剣で、エージェントがデバッグデータを残していくと、プレビューは時間とともに本番からずれていきます。

## 配線はどう見えるか

それぞれのスケッチで、完全な設定ではありません。

<CodeTabs>

**Vercel:リポジトリを接続すると、PR ごとに自動プレビュー。**

```bash
# vercel.json (defaults handle most cases)
{
  "github": { "silent": true },
  "buildCommand": "pnpm build",
  "outputDirectory": ".next"
}
# Vercel posts the preview URL to the PR automatically.
```

**Cloudflare Pages:Wrangler 経由で同様の形。**

```toml
# wrangler.toml
name = "my-app"
compatibility_date = "2026-04-01"
pages_build_output_dir = "dist"
# Preview URLs auto-generated per PR; bind in Pages dashboard.
```

**ワークステーション上の永続ランタイム:開発サーバーがプレビュー。**

```bash
# On the workstation, agent runs:
pnpm dev --port 3000
# Workstation issues a stable preview URL bound to port 3000.
# The URL stays the same across commits; the content updates live.
```

## コストとループ速度はトレードオフになる

パレート最適な答えはありません。正しい選択はワークロード次第です。

<Callout variant="info" title="トレードオフの形">
PR ごとのエフェメラル・プレビューは、ビルドあたり安価で変更あたりが遅い。永続ランタイム・プレビューは、ワークステーションあたり高価で変更あたりが即時。エージェントが1日2回反復すれば、エフェメラルが勝ちます。エージェントが1日20回反復すれば、永続が勝ちます。クロスオーバーは1日5回反復のあたりで、ビルド時間が正確な位置を決めます。
</Callout>

ビルド時間が最大の変数です。30秒のビルドは多数の反復にうまく償却されます。5分のビルドは違います。ほとんどのエージェント型チームは、エージェントがビルドを待って1時間焼くのを2回見たあとで、永続ランタイム・プレビューに手を伸ばします。

## Codespaces はどうか

Codespaces は別の形です。ワークスペースがプレビューですが、Codespaces は人間向けに作られました。エージェントのゲートなし、parallel-agent の隔離なし、`git push` の passkey なし。作業が人間主導ならプレビュー・ランタイムとして使えます。エージェントが主たるユーザーになると、ランタイムとしては不十分です。長めの比較は[Codespaces vs Ellul](/vs/codespaces)を参照してください。

## では、どちらを選ぶか

作業がほぼステートレスなウェブフロントエンドで、エージェントが1日数回コミットするなら、Vercel スタイルのエフェメラル・プレビューが最もきれいな答えです。スタックがエッジ・ネイティブなら、Workers のプレビューがコールドスタートを改善した同等品です。エージェントが数分ごとに反復し、ループ速度が重要なら、ワークステーション上の永続ランタイム・プレビューが、より高い月額コストを節約された時間で取り戻します。

これらの前に答えるべき、より深い問いは:エージェントが「完了」と言ったとき、誰が作業をレビューするか?答えが「差分」なら、プレビュー基盤は怠けて構いません。答えが「URL」なら、それはできません。2026年のほとんどのエージェント型チームでは、答えは URL です。
