2026年4月時点で、エージェント型コーディングには2つの異なる製品形態が現れていますが、カテゴリ名はまだ追いついていません。一方には Devin、Manus、Bolt、Lovable、base44 のようなベンダー管理型エージェントがあります。ベンダーがエージェントを売り、モデルを選び、ランタイムを所有し、エンドツーエンドの製品を提供します。もう一方には bring-your-own-agent ランタイム(Ellul と、いくつかのセルフホスト構成)があり、既存のエージェント CLI をそのまま使い、プラットフォームはその下のランタイムだけを売ります。

両者のどちらかを選ぶときは、それぞれが答える問いを理解しておくと役に立ちます。

## 2つの形態を一段落ずつ

**管理型エージェント**はターンキー製品を売ります。チャットボックスに作業を記述します。ベンダーのエージェントが、ベンダーのモデル上で、ベンダーのサンドボックス内で結果を生成します。PR、デプロイ済みアプリ、リサーチ文書などです。Devin が代表例で、意見の強い構成で、Devin 2.0(2025年4月)以降は従量課金、月$20の Core プラスおよそ $2.25/Agent Compute Unit、その上に Pro と Max の上位ティアがあります。Manus は汎用版で、クレジットベースの料金とエージェント主導のリサーチが特徴です。Bolt と Lovable はウェブサイト寄り。base44 は同カテゴリのノーコード寄りに位置します。

**bring-your-own-agent ランタイム**はインフラを売ります。既存のエージェント CLI を、プラットフォームが管理する永続的なリモートワークステーションにインストールします。CLI はこれまで通り動作します。プラットフォームが提供するのは、ノートPC上の CLI にはないランタイム特性です。フタを閉じてもセッションが生き残ること、状態の衝突なく並列実行できること、`git push` のような特権アクションを passkey の背後にゲートすることなどです。モデルベンダーとの BYOK 関係、CLI で慣れた操作感、コードベースの所有権はあなたの手元に残ります。私たちが構築したのは、このカテゴリの [Ellul](/) です。

これらは同じ買い物ではありません。コスト構造が違い、ロックインの仕方が違い、卒業したくなったときの抜け方も違います。

## コストは実際どう比較されるのか

表面の価格は分かりやすく見えます。実コストはもっと曖昧です。

<BulletList>
  <BulletItem heading="管理型エージェントの表面価格">
    Devin 2.0 は月$20の Core から始まり、概ね $2.25/Agent Compute Unit の従量課金、Pro・Max の上位ティアと企業向け価格があります。Manus Plus は月およそ$39でクレジットベース。Bolt と Lovable は月$20から$25あたりから始まり、トークン使用量の上限が付きます。base44 はノーコード寄りで低価格帯。表面価格には通常モデルが含まれていて、別途支払う必要はありません。
  </BulletItem>
  <BulletItem heading="BYOA の表面価格">
    Ellul は個人ティアが月$20、プロが月$50です。これにモデルは含まれません。モデルベンダー(Anthropic、OpenAI、その他)に対しては、自身の API キーで直接支払います。利用量が多い場合、モデル代の方が大きな項目になります。
  </BulletItem>
  <BulletItem heading="実コスト:ヘビーユース">
    Anthropic の Pro($20)または Max($100または$200)を使う Claude Code のヘビーユーザーが Ellul のプロ($50)を組み合わせると、合計は月$70から$250の範囲に収まります。Devin のヘビーユーザーが付属クレジットを超えて継続的に使うと、ACU 課金で月$200を超えるのが普通で、同じ作業量では Ellul と Claude Max の合計を上回ることもあります。差は使い方次第でどちらにも振れますが、構造的な違い(誰のモデルか、誰のワークフローか)は変わりません。
  </BulletItem>
  <BulletItem heading="実コスト:ライトユース">
    ライトユーザーは Cursor Pro($20)または Claude Pro($20)に Ellul の個人ティア($20)を加えて、月$40。Manus のライトユーザーはおよそ$39。ほぼ同じです。
  </BulletItem>
</BulletList>

構造的なコスト差は、金額そのものではありません。**意見強要税**です。管理型エージェントは、自社のモデル、自社のワークフロー、自社のツールスタックを焼き込みます。乗り換えはリプラットフォーム作業になります。BYOA はそれらを切り離すので、これは一度きりの大きな節約というより、繰り返し発生する小さな節約です。

## ロックイン、もう少し正直に

ロックインの話は退屈に聞こえるので軽く流されがちです。実際は軽くないです。

**管理型エージェントはベンダーのモデルにロックインします。** Devin のスタックは Cognition のものです。Manus のスタックは Manus のものです。ベンダーのモデルが退化したら、製品ごと乗り換えない限り別のモデルに切り替えることができません。フロンティアモデルが数か月ごとに変わる年において、これは現実的なリスクです。(注:Cursor の Cloud Agents はここで興味深いハイブリッドです。ランタイムは管理されているがモデル選択は同じほど意見を強要されない。)

**管理型エージェントはベンダーのワークフローにロックインします。** Devin は Devin のコミットメッセージスタイルで PR を開きます。Manus は Manus のフォーマットで文書を生成します。チームに強い好み(コミット規約、コードレビュースタイル、ドキュメントテンプレート)があれば、製品と戦うかベンダー版を受け入れるかの二択です。

**管理型エージェントはベンダーの認証情報モデルにロックインします。** Devin は GitHub の認証情報を Devin の中に保持します。Manus はツールのトークンを Manus の中に保持します。認証情報を別の場所(自社の vault、IAM、シークレットマネージャー)に置きたくても、管理型エージェント製品は通常それをサポートしません。エンジニアが1人を超えると、これが効いてきます。

**BYOA はこの3つすべてを切り離します。** エージェントはあなたのもの。モデル契約はあなたのもの。ワークフローはあなたのもの。プラットフォームが所有するのはランタイムだけです。卒業コストはエージェント CLI を別のランタイムに移すことで、四半期ではなく時間単位で測れます。

複数年にわたって見れば、これは本当のお金です。同時にエンジニアリング文化でもあります。職人気質を重視するチームは、2010年代にローコードを嫌ったのと同じ理由で、意見強要型のエンドツーエンド・エージェント製品を嫌う傾向があります。

## 管理型が本当に向いているのはいつか

実ユーザーの多くは管理型エージェントで適切に対応できます。形が合わないのに無理に当てはめると、ミスマッチが起きます。

<NumberedList>
  <NumberedItem heading="単発の作業">
    リサーチプロジェクト、マーケティングサイト、独立スクリプト。既存のコードベースやエージェント構成と組み合わせる必要がない作業です。管理型エージェントの方が始めるのは速いです。自前のランタイムを持ち込む統合コストは余計な負担になります。
  </NumberedItem>
  <NumberedItem heading="エージェントを運用するエンジニアリングチームがいない">
    プロダクトマネージャー、研究者、非エンジニアの創業者など。ワークステーションのセットアップ、エージェント CLI の設定、BYOK 鍵の管理は本当の手間です。管理型エージェントはこれらを代行してくれて、それは支払う価値があります。
  </NumberedItem>
  <NumberedItem heading="ベンダーのモデルが正しいモデル">
    Cognition のスタックは、特定種類のエンジニアリング作業には実際に強いです。A/B テストして、自分の作業について Devin が Claude Code 構成より良い結果を出すなら、正解は Devin を使うことです。
  </NumberedItem>
  <NumberedItem heading="ベンダーのワークフローがあなたのワークフロー">
    チームにコミットスタイルや PR の形について強い好みがなければ、ベンダーのデフォルトで構いません。意見がなければ意見強要税は発生しません。
  </NumberedItem>
</NumberedList>

この4つのうち3つが当てはまるなら、管理型が正解です。逆らわないでください。

## BYOA が本当に向いているのはいつか

対称な視点から。

<NumberedList>
  <NumberedItem heading="継続的なエンジニアリング作業">
    エージェントが、毎日の出荷の一部になっている。統合の深さ(リポジトリの規約、ツール、CI、モニタリング)が、表面のターンキー性より重要です。BYOA は数か月で元を取ります。
  </NumberedItem>
  <NumberedItem heading="気に入っている既存のエージェント CLI">
    チームに Claude Code の操作感が染み付いている、Cursor の command-K の操作感、Codex のパイプラインの操作感などです。管理型製品に切り替えてもらうのは学び直しを強いることです。多くの場合、CLI を残してその下のランタイムを変えるのが正しい一手です。
  </NumberedItem>
  <NumberedItem heading="規模拡大時のコスト規律">
    エンジニアが10人いる。管理型エージェントの料金はシート単位で線形に増えます。BYOA はワークステーション単位、モデル代は実使用量単位なので、サブリニアにスケールします。損益分岐点は5人前後で、もっと早いことも多いです。
  </NumberedItem>
  <NumberedItem heading="マルチモデル戦略">
    あるタスクには Claude、別のタスクには OpenAI、トリアージにはオープンウェイトのローカルモデル、というように使い分けたい。管理型エージェントはこれに応じません。BYOA は鍵とエージェントを持ち込めるので応じます。
  </NumberedItem>
  <NumberedItem heading="本物の認証情報を扱うオペレーション">
    エージェントが本番にプッシュし、デプロイし、データベースマイグレーションを実行する必要がある。あらゆる特権アクションを単一の機構でゲートし、単一の監査ログにしたい。BYOA で passkey ゲートの境界を置けばクリーンに実現できます。管理型エージェントは認証情報をサンドボックス内で扱いますが、それは問題が起きるまでは問題ない、という性質のものです。
  </NumberedItem>
</NumberedList>

5つのうち3つが当てはまれば、BYOA がおそらく正しい形です。アーキテクチャ面の長めの議論は[エージェントワークステーション](/concepts/agent-workstation)を参照してください。

## では、どちらを選ぶべきか

愛用しているエージェント CLI がなく、作業が単発で、ベンダーのモデルがその作業に正しいモデルなら、管理型を選んでください。エージェントがチームの継続的な出荷の一部で、すでに使っている CLI があり、長期の特性(マルチモデル戦略、コスト規律、本物の認証情報ゲート)を気にするなら、bring-your-own-agent を選んでください。

間違いは、ハイプで選ぶことです。今年、管理型エージェントの方がマーケティングの声が大きい。bring-your-own-agent ランタイムは静かです。声の大きさはシグナルではありません。あなたの作業が実際何で、これから2年それを増やすにはどの形が適しているかを見てください。

具体的な比較対象については、[Devin vs Ellul](/vs/devin)、[Manus vs Ellul](/vs/manus)、そして[エージェントワークステーション](/concepts/agent-workstation)の入門を参照してください。
