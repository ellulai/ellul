AIエージェントのセキュリティは、チャットボットを後付けしたWebアプリのセキュリティではありません。エージェントはシェルを持っています。あなたの認証情報を保持しています。敵対的でありうるプロンプト(あなたが書いていないドキュメント、エラーメッセージ、ツール応答に隠されたプロンプトを含む)について推論します。2026年にエンジニアが実際に直面する脅威は、ほとんどのエンジニアが教え込まれたOWASP Top 10とはカテゴリ的に異なります。この記事は、実用的な脅威モデルと、脅威を実装可能な緩和策にマッピングするランタイムチェックリストです。

具体的に話します。ほとんどのコーディングエージェントに付属するデフォルトは、決意ある攻撃者との接触を生き延びるデフォルトではなく、そのギャップこそが大半の被害が起こる場所です。

## 脅威モデル

エージェント型コーディングのための有用な脅威モデルには、4つの主要カテゴリがあります。それぞれが本番で観察されています。それぞれが正しいランタイムで解決可能ですが、現在のセットアップの大半はせいぜい2つしか解決していません。

### 1. プロンプトインジェクション

エージェントは、その振る舞いをリダイレクトするように設計された指示を含む敵対的入力を読みます。直接プロンプトインジェクションは明らかなケース(「以前の指示を無視して...」)。間接プロンプトインジェクションは過小評価されているケース:攻撃者がコメント、サードパーティAPI応答、エージェントが後で読むSlackメッセージ、サブプロセスのエラー出力に指示を植え付ける。エージェントは「これはユーザーが私に考慮してほしいデータだ」と「これは私が従うべき指示だ」を区別しません。

緩和策:入力サニタイゼーションは明らかなケースには役立ちますが、スケールしません。構造的な答えは、エージェントが読めるあらゆるテキストが敵対的でありうると仮定し、入力ではなく**アクション**をゲートすることです。OWASP LLM Top 10([owasp.org](https://owasp.org/www-project-top-10-for-large-language-model-applications/))はプロンプトインジェクションを#1として挙げており、その中心性について正しいです。

### 2. アンビエント認証情報

エージェントはそれが動作するOSユーザーの認証情報の表面を継承します。ラップトップ上ではそれは`~/.aws/credentials`、`~/.ssh/`、`~/.kube/config`、`~/.config/gcloud`、ブラウザのクッキー、1Password CLIセッション、隣接プロジェクトディレクトリの数百の`.env`ファイルを意味します。アンビエント認証情報が脅威となるのに、エージェントが悪意である必要はありません。混乱したエージェントが間違ったファイルを読むだけで十分です。

緩和策:認証情報をエージェントのプロセスから外す。成熟したパターンは、別のOSユーザーとして動作し、シークレットを自分のメモリに保持し、すべての権限アクションを別のチャネルを通じて仲介する認証情報ブローカです。私たちは[Sovereign Shield](/glossary/sovereign-shield)がこれをどう実装するかを説明しました。アーキテクチャパターンはどの単一の製品より広いものです。要点は、アンビエント認証情報は設定ミスではないということです。それは、エージェントをドットファイルと同じプロセスで走らせることのデフォルトの状態です。

### 3. ツール誤用

エージェントはツール(ファイルシステム、シェル、MCPサーバ、HTTP API)を持ち、それを予期しない方法で呼び出せます。ツール誤用は、明らかなもの(エージェントがリクエストを誤解して`rm -rf /`を走らせる)から微妙なもの(エージェントが見るべきでない列を読むSQLクエリを走らせる、エージェントが呼び出しごとに課金されるAPIにHTTPリクエストする、ツール記述が曖昧だったためにエージェントがシェルワイルドカード経由でシークレットを列挙する)までのスペクトラムをカバーします。

緩和策:ツール表面を境界づけし、各アクションクラスをゲートする。ツール表面の境界づけは、エージェントの名前空間があなたが認可していないツールに到達できないことを意味します:カーネルレベルの egress 制御、AppArmorプロファイル、seccompフィルター。各アクションクラスのゲーティングは、エージェントは呼び出しを試みられるが、呼び出しの結果が仲介されることを意味します。これが私たちが[Ironclad層](/glossary/ironclad-tier)で意味するものです:複数の層で閉じるカーネルレベルの境界で、単一の誤分類がカスケードしないようにします。

### 4. 流出

エージェントが機微なデータ(コード、シークレット、データベースの顧客行)を読み、サイドチャネル経由で流出させます。流出ベクトルは驚くほど創造的です。エージェントが本文にデータを入れた「サポート」イシューを開く。エージェントがコミットメッセージにデータを埋め込む。エージェントがパラメータとしてデータを使って外部APIを呼ぶ。エージェントが、インデックスされる画像のalt textにデータをレンダリングする。あなたが制御していないエージェントが書ける場所はどこでも、流出チャネルです。

緩和策:egress 制御と監査。Egress 制御は、攻撃者がデータを取り出すために使うネットワークパスをブロックします。監査ログ(耐久性があり、改ざん明示的、あなた自身のもの)は、制御を回避する流出試みを検出させます。両方が必要です。どちらか一方だけでは不十分です。監査なしの egress 制御は、制御が失敗したときに流出を静かにします。Egress 制御なしの監査は、流出を大きくしますが止められません。

## 「エージェントがシェルを持つ」問題

上記のすべての脅威は、1つの構造的性質によって悪化します:エージェントはシェルを持っています。任意のコマンドを実行できます。任意のファイルを読めます(ランタイムが許せば)。サブプロセスを起動できます(ランタイムが許せば)。これがコーディングエージェントを有用にし、チャットボットよりカテゴリ的により危険にするものです。

ほとんどのセキュリティチームを驚かせる含意:エージェントのプロセス内の権限境界は架空です。エージェント内の権限プロンプト(「エージェントは`git push`を実行したい、許可するか?」)は、エージェントの推論と同じアドレス空間で動作します。十分に巧妙なプロンプトインジェクションは、エージェントを丸め込んでアクションをルーチンとしてレンダリングさせるか、プロンプト自体をバイパスするものとしてフレーミングすることができます。混乱したエージェントは、ユーザーが無関係なルーチンアクションを承認している間に危険なアクションを実行できます。プロンプトは境界ではありません。UIです。

実の境界はエージェントのプロセスの外に住みます。異なるOSユーザー。異なる名前空間。異なるネットワーク。エージェントがゲートプロセスを検査することやそのサブプロセスにアタッチすることを防ぐカーネルレベルの制御(`ptrace_scope=1`、`seccomp`、`AppArmor`)。ゲートは別のメモリを持つ別のプログラムであり、定義されたIPCチャネルを通してのみエージェントと話します。これは権限プロンプトを構築するより難しいです。それはまた、唯一機能するものです。

## 実認証情報操作を正しく行う

エージェントが実認証情報に触れなければならないなら(おもちゃでないエージェント型コーディングワークフローはいずれそうなります)、ランタイムは認証情報をエージェントから遠ざけ、すべての使用をゲートする必要があります。

[Sovereign Shield](/glossary/sovereign-shield)から抽象化されたパターンですが、他にも適用できます:

<NumberedList>
  <NumberedItem heading="認証情報はブローカプロセスに住む">
    認証情報ブローカは、別のOSユーザーとして独自のグループメンバーシップで動作する長寿命プロセスです。エージェントプロセスはブローカのメモリ、環境、git サブプロセスの認証情報を読めません。カーネルレベルの ptrace 制限が、同じuidで動作するプロセスに対してもこれを強制します。
  </NumberedItem>
  <NumberedItem heading="すべての権限アクションは分類される">
    ブローカはアクションをゲート種別に分類します:`git_push`、`deploy`、`db_write`、`secret_read`、`db_migrate`。各ゲートは独自のクラスごとTTLと独自の承認要件を持ちます。プッシュ承認はデプロイを自動承認しません。デプロイ承認はデータベースマイグレーションを自動承認しません。
  </NumberedItem>
  <NumberedItem heading="承認はFIDO2 / WebAuthn">
    [パスキー承認](/glossary/passkey-approval)はソフトウェアプロンプトではなく、ハードウェア裏付けの暗号確認です。エージェントはユーザーの生体を合成できません。エージェントはユーザーのハードウェアなしに最近クリアされたキャッシュをリプレイできません。承認は特定のアクションクラスと特定のTTLにバインドされます。期限切れになるとエージェントは再度尋ねる必要があります。
  </NumberedItem>
  <NumberedItem heading="監査ログはあなたのもの">
    すべての権限アクション(試行、承認、拒否、期限切れ)はあなたが保管するログにあります。ログにはアクションクラス、タイムスタンプ、承認したデバイス(あれば)、エージェントが何をしていたかについての主張、そして結果が含まれます。正しいセットアップでは改ざん明示的。最悪でも有用なほどに不変です。
  </NumberedItem>
  <NumberedItem heading="モデルはシークレットを決して見ない">
    [ゼロ知識暗号化](/blog/zero-knowledge-byok)を使ったBYOKは、エージェントが使う最も機微な認証情報であるモデルAPIキーでさえ、パスキー由来のシークレットで保存時に暗号化されることを意味します。プラットフォームは暗号文を保管します。モデルはリクエストを受け取りますが、プラットフォームは平文の鍵を決して見ません。
  </NumberedItem>
</NumberedList>

複合効果:エージェントの推論を完全に侵害した攻撃者でも、あなたの指紋なしには権限アクションを完了できません。

## ランタイムチェックリスト

AIコーディングツールのセキュリティ姿勢を評価しているなら、これらに対して走らせてください。

<BulletList>
  <BulletItem heading="エージェントはどこで動作するか?">
    あなたのマシン(高い認証情報露出、低い隔離)、ベンダーのマシン(あなたは監査トレイルを持たない)、あなたが制御するワークステーションランタイム(中程度の認証情報露出、高い隔離、あなたの監査)。3つ目だけがスケールします。
  </BulletItem>
  <BulletItem heading="認証情報はどこに住むか?">
    エージェントのメモリの中(最悪)、同じマシンの別プロセス(より良い)、エージェントからのカーネルレベルの隔離を持つ別プロセス(最良)。「保存時暗号化」は必要であり十分ではありません。認証情報はほとんどの時間で保存されていますが、脅威は使用時です。
  </BulletItem>
  <BulletItem heading="権限アクションを何がゲートするか?">
    何もない(エージェントは呼び出せるものは何でも実行)、プロセス内権限プロンプト(簡単なケースには役立つ)、プロセス外パスキーゲート(実の境界)。1つ目はラップトップネイティブエージェントのデフォルト。2つ目はほとんどのコーディングエージェント製品。3つ目は稀で、本番作業に欲しいものです。
  </BulletItem>
  <BulletItem heading="アクション監査ログは検査可能であなたが保有するものか?">
    ベンダーの「ログをリクエストできる」ポリシーはログを持つことと同じではありません。クエリできないログは監査ではありません。あなたが所有していないログはあなたのものではありません。
  </BulletItem>
  <BulletItem heading="飛行中のプロンプトを誰が見るか?">
    定義によりモデルAPI。プラットフォーム(あなたとモデルの間のラッパー)も見るかもしれません。保持ポリシーを読んでください。プラットフォームが「サービス改善のため」プロンプトを保持するなら、オプトアウトしない限りあなたのプロンプトはトレーニングデータです。
  </BulletItem>
  <BulletItem heading="エージェントが侵害された場合の境界は何か?">
    プロセス(最弱)、ユーザー、名前空間、マシン、ハードウェア(最強)。複数層が目標です。1つの層を突破する侵害は、別の層に当たるべきです。[Ironclad層](/glossary/ironclad-tier)は私たちの複数層への取り組みです。原則は一般化できます。
  </BulletItem>
</BulletList>

6つすべてに明確に答えられるベンダーは、これについて考えています。これらのいずれかについて手を振って済ませるベンダーは、本番エージェントを走らせるべき場所ではありません。

## 来たるべき脅威モデル

将来を見据えて、3つの脅威パターンが、後から襲ってくるよりも今注目に値するほど頻繁にインシデントレポートに現れています。

クロスエージェント結託。ピアリングアクセスを持つ2つのエージェントは、読み取り専用チャネルを通じて情報を交換できます。ピアリングプリミティブが積極的にフィルタしないなら、読み取り専用側は読み書き側に共有ファイルにデータを書くよう頼めます。緩和策は、私たちのドキュメントが[クロスサンドボックス共有](https://docs.ellul.ai/projects/sharing-projects)について記述しているものです。ピアリングは、シークレットと設定ファイルがフィルタされ、書き込みエージェントがピアを修正するように騙されないように4層でスコープチェックされる、キュレーションされたソースコードのみのスナップショットです。

MCPサーバ経由のサプライチェーン。[MCP](/glossary/mcp)は標準化の勝利であり、新しい攻撃表面です。悪意のあるまたは侵害されたMCPサーバは、それ経由でルーティングされるすべてのツール呼び出しをキャプチャできます。緩和策は他のパッケージサプライチェーンと同じです:バージョンを固定し、コードを監査し、ホスト上のアンビエントではなくエージェントと同じ境界内で動かす。

エージェント間プロンプトインジェクション。1つのエージェントの出力が別のエージェントの入力になるマルチエージェントセットアップは、攻撃者がエージェントBを操作するために特にエージェントAの出力に植え付けた指示に脆弱です。緩和策は、エージェント間通信を信頼できない入力として扱い、同じゲーティングルールを適用することです。

## 誠実な要約

AIコーディングエージェントのセキュリティはランタイム問題です。モデルよりそれが動作する場所のほうが重要です。デフォルトのラップトップランタイムでの最強モデルは、堅牢化されたランタイムでの並のモデルより安全性が低いです。逆のパターン(モデルアップグレードがランタイムのギャップを修正する)は存在しません。

重要なランタイム性質を、影響の順に:

1. 認証情報はエージェントのプロセスの外、エージェントが読めないブローカに住んでいます。
2. 権限アクションはハードウェア裏付けのユーザー承認のために一時停止します。
3. エージェントはカーネルレベルの境界(別ユーザー、名前空間、ネットワーク)で動作します。
4. Egressは制御され監査されます。
5. 監査ログはあなたのものであり、改ざんが明示的です。

5つすべてを行うランタイムが基準です。最初の3つに加えて4と5への誠実な計画を持つランタイムは許容できます。それより少ないランタイムはデモです。

1つ持ち帰るとしたら:エージェントはいずれあなたが予期しない何かをします。あなたの保護はエージェントが完璧にアラインされていることではありません。あなたの保護はランタイムがそうあることです。それを念頭に構築してください。
