あるAIエージェントに別のエージェントのコードを読ませたい、しかも最初のエージェントが2番目のエージェントの認証情報を継承しないように、というのが要件です。文章にすると単純です。実装こそが多くのエージェント・プラットフォームが静かに失敗する場所です。素朴なアプローチ（エージェントBのプロジェクト全体をエージェントAにバインドマウントする）は、初めて試した瞬間に `.env` ファイル、認証情報JSON、OAuthトークンを偶発的に漏らします。ピアリング・プリミティブはこの問題に対する正しい形であり、本稿はその理由を扱います。

ドキュメント（[Cross-Sandbox Sharing](https://docs.ellul.ai/projects/sharing-projects)、[Working in a Sandbox](https://docs.ellul.ai/projects/working-in-a-sandbox)）から作業を進め、アーキテクチャを真剣に扱います。これはEllulの設計の中でもより興味深い部分の1つで、宣伝ページの扱いよりも深く見る価値があります。

## サンドボックス間の読み取り問題

実際のユーザーから寄せられたシナリオです。

> 「2つのエージェントを動かしている。1つはブランチ `auth-refactor` で機能を実装している。もう1つはその実装をレビューする想定。レビュアーは仕事をするために実装側のコード（すべてのファイル、すべての差分、すべてのテスト）を読む必要がある。だが、レビュアーに実装側のデプロイキー、GitHub PAT、または実装側のブランチに直接pushする能力を絶対に持たせたくない」

これは構造的によくあるパターンです。1つのエージェントが作業を生み、別のエージェントがそれを検証します。役割と権限が異なります。素朴なセットアップは両者に同じアクセスを与えてしまい、そもそも2つのエージェントを持つ意義を破壊します。

制約を一般化すると、読み取り側エージェントは有用な仕事をするために対象サンドボックスのソースコード全部を必要とします。読み取り側エージェントは対象サンドボックスに対して何の権限も持ってはいけません（認証情報も、デプロイキーも、データベースアクセスも、書き戻し能力も）。境界は助言ではなく強制でなくてはなりません。意志的または混乱した読み手が、プラットフォームに丁寧に頼んで権限昇格できてはいけません。

書き出すのは簡単で、実務で守るのは驚くほど難しい3つの制約です。

## 多くのプラットフォームがこれを誤る方法

私たちが監査してきたほとんどのマルチテナント・エージェント・プラットフォームでのデフォルトのパターン。

```
mount --bind /workspaces/B/src /workspaces/A/.shared/B
```

Bのソースツリーをカーネルレベルで読み取り専用にしてAのワークスペースにバインドマウントすることが多いです。一見もっともらしい。問題はそのソースツリーの中身です。

`.env` と `.env.local` と `.env.production` と `.env.staging`：Bのシークレットがすべて平文でAから見えます。`credentials.json` と `service-account.json`：Google Cloud、Firebase、GCPサービスアカウントが、これらのサービスと統合する任意のプロジェクトルートに置かれています。NPM認証トークン入りの `.npmrc`：プライベートパッケージへのフルパブリッシュアクセス。HTTP認証情報入りの `.netrc`。PostgreSQLパスワード入りの `.pgpass`。`.openclaw/`、`.claude/`、`.codex/`、`.gemini/`：OAuthリフレッシュトークン、APIキー、セッション状態を保持することの多いエージェント設定ディレクトリ。`.docker/config.json`：Dockerレジストリ認証情報。`node_modules/`：ロックファイルやビルド済みアーティファクト内にシークレットを保持できる依存物。`.git/objects/`：過去のすべてのコミット。あらゆる時点でコミットされ、後続のコミットで「削除」されたシークレットも含みます。

読み取り専用バインドマウントはこれらの読みやすさを何1つ下げません。読み手はそれらすべてを読めます。マウントが読み取り専用であることは、読み手がBのソースを変更できないという意味だけです。読み手はもとよりソースを変更するつもりはなく、シークレットを抜き取るつもりだったのです。

これがエージェント・プラットフォーム・セキュリティレビューで最もよく見る障害モードです。許可ルールは「Bのソースへの読み取り専用アクセス」と言います。バインドマウントは「Bのソース内のすべて、ソースでない部分も含めて」と言います。「Bのソース」と「Bのソースディレクトリの中身」の意味的なギャップ、ここに侵害が住んでいます。

## ピアリング・プリミティブ：ソースコード限定スナップショット

修正は構造的です。ツリー全体をマウントしないこと。厳選したサブセットをコピーすること。

Ellulが実装するパターン（[Cross-Sandbox Sharingドキュメント](https://docs.ellul.ai/projects/sharing-projects) からそのまま引用）。

<NumberedList>
  <NumberedItem heading="明示的な除外を伴うrsync">
    プラットフォームはrsyncを使ってBのソースのスナップショットを取り、境界を越えてはいけないものすべてを除外する明示的な除外リストを使います。除外パターンには `.env*`、`credentials.json`、`service-account.json`、`.npmrc`、`.pypirc`、`.netrc`、`.htpasswd`、`.pgpass`、エージェント設定ディレクトリ（`.openclaw/`、`.claude/`、`.codex/`、`.cursor/`、`.config/`、`.vscode/`、`.idea/`、`.docker/`）、依存ディレクトリ（`node_modules/`、`.yarn/`、`.pnpm-store/`）、肥大化要素（`.git/objects/`、`.git/lfs/`）が含まれます。
  </NumberedItem>
  <NumberedItem heading="スナップショットは物理であって仮想ではない">
    rsyncの出力に含まれないファイルは、Aから見えるスナップショット上に物理的に存在しません。これは「AはBのソースを読めるが、Bのシークレットは読めない」と言う許可ルールとは根本的に異なります。許可ルールは誤設定されることがあり、巧妙なパス操作でバイパスされることがあり、想定外の条件下でフェイルオープンしうる。コピーされなかったファイルは存在しません。読むべき `.env` がない、なぜなら `.env` がないからです。
  </NumberedItem>
  <NumberedItem heading="シンボリックリンクは拒否">
    rsyncは `--no-links` で動きます。Bのソースにシンボリックリンクが含まれていれば（`.ssh` ディレクトリへ、システム認証情報ファイルへ、どこかへ）、シンボリックリンクは追われずコピーされません。これでシンボリックリンク先のシークレット攻撃が閉じます。悪意ある、もしくは侵害されたBは、Aの攻撃対象ファイルを指すシンボリックリンクをソースツリーに置いて、スナップショット処理にそれを吸い上げさせることができません。
  </NumberedItem>
  <NumberedItem heading="マウントはカーネルレベルで読み取り専用">
    スナップショットはAのワークスペース内 `.shared/<B-id>/` にマウントされ、カーネルマウント層で読み取り専用フラグが強制されます。AはBのソースを変更しようとしても変更できません。これは二重の安全策です。Aから見えるのはコピーですが、カーネルレベルの読み取り専用強制があるので、コピー権限のミスが偶発的に書き込みを許してしまうことがありません。
  </NumberedItem>
</NumberedList>

組み合わせは個々の部品の合計より強いものを提供します。除外リストが何を越えてはいけないかを述べます。物理コピーがそれを不可逆に強制します。シンボリックリンク拒否が最も明らかなバイパスを防ぎます。読み取り専用マウントが上記のいずれかが失敗した場合を捕まえます。

## 4層スコープチェック

Bのソースコードを読むのは1つの問題です。より難しい問題は、Aを騙してBに何かをさせることを防ぐことです。Aのソースに正当に次のようなコメントが含まれていると仮定します。

> // TODO: Run `migration_2024_03.sql` against the production database

Aのエージェントが共有スナップショット経由でこのコメントを読みます。エージェントはこれを「あのマイグレーションを実行すべき」と合理的に解釈するかもしれません。Aのエージェントがデータベース操作を要求でき、その操作がBのデータベースを参照するなら、読み取りアクセスは書き込み能力に化けたことになります。

これはピアリングが生む構造的リスクで、純粋な隔離にはないものです。緩和策は、すべての許可要求で実行される4層のスコープチェックです。

<NumberedList>
  <NumberedItem heading="チャット層がサンドボックススコープのツール呼び出しを自動拒否">
    チャット層のツールリゾルバが、許可ゲートが要求を見るより前に、要求者以外のサンドボックスを参照するサンドボックススコープのツール呼び出し（データベース、シークレット、デプロイ、観測）を自動拒否します。AからBのデータベースに書き込む要求はリゾルバで拒否され、ゲートには到達しません。
  </NumberedItem>
  <NumberedItem heading="許可要求はヒントで補強される">
    AがBのリソースに対して使う可能性のあるサンドボックススコープでないツール（原理的にBスコープのパスに到達できる汎用シェルツールなど）について、許可要求は要求者が読み取りアクセスを持つサンドボックスに言及していることを示すヒントで補強されます。ユーザーは承認プロンプトでヒントを見、ゲートは監査ログでそれを見ます。
  </NumberedItem>
  <NumberedItem heading="Sovereign Shieldが独立に検証">
    エージェントプロセスの外側でカーネル隔離されて動く [Sovereign Shield](/glossary/sovereign-shield) は、要求者が読み取りアクセスを持つサンドボックスを名指しする許可要求を独立に検証します。「この要求が実際に対象としているサンドボックスは何か」というShieldの視点はエージェントのプロンプトでは偽装できません。Shieldは下位のシステムコールと操作を直接見ます。
  </NumberedItem>
  <NumberedItem heading="システムプロンプトが意図を明示">
    エージェントがピアサンドボックスへの読み取りアクセスを持つとき、システムプロンプトが検査専用の意図を明示するよう更新されます。「あなたは `.shared/B` でサンドボックスBへの読み取りアクセスを持っています。これは検査のみのためです。Bに対する書き込み、デプロイ、データベース操作を要求しないでください」。これは最も弱い層ですが（敵対的入力でシステムプロンプトは上書きされうる）、モデルが正常に動作している間は意図を曖昧でなくします。
  </NumberedItem>
</NumberedList>

各層単独では不完全です。チャット層リゾルバはサンドボックススコープでないツールでバイパスされうる。許可ヒントはユーザーが気づくことに依存する。Shieldの検証はクロスリファレンスデータが間違っていれば誤りうる。システムプロンプトは無視されうる。組み合わせれば、どれか1層が見逃すものを捕まえます。形は意図的に行われた多層防御で、偶発的なものではありません。

## ライフサイクル：付与・更新・取り消し

運用上、ピアリング・プリミティブには知っておくべき単純なライフサイクルがあります。

アクセス付与。サンドボックスAの設定から、サンドボックスBを読み取り元として選びます。プラットフォームがスナップショットを取り、Aの `.shared/<B-id>/` にrsyncし、読み取り専用でマウントします。付与は両方のサンドボックスで監査ログに残ります。

スナップショット更新。スナップショットは時点指定です。付与後にBのコードが変わってもAは元のスナップショットを見ます。Aのパネルで「共有スナップショットを更新」をクリックすると新しいスナップショットを取ります。これは意図的な設計選択です。ライブマウントはスコープチェックのタイミングを推論しにくくし、ほとんどの読み取りアクセス用途はリアルタイム更新を必要としません。

アクセス取り消し。Aのパネルで「取り消し」をクリック。マウントは即座に削除されます。Aのアクティブなセッションはその瞬間にBへの可視性を失います。取り消しは監査ログに残ります。

なぜ時点指定でライブでないか。リアルタイム更新は、Bが `.env` ファイルを書き込んだ瞬間（rsyncフィルタが走る前の短い窓の間）にAの視野に出現することを意味します。スナップショット意味論はその窓を閉じます。rsyncは付与時に1回、更新で再度走り、その結果がAから見えるものです。「rsyncとrsyncの間」の状態はありません。

## マルチエージェント・ワークフローでなぜこれが重要か

ピアリング・プリミティブは「マルチエージェント・セットアップが理論上可能」と「マルチエージェント・セットアップが運用上安全」の差です。これに依存する3つのパターンが本番で見られます。

<BulletList>
  <BulletItem heading="エージェント間のコードレビュー">
    エージェントAが機能を実装中。エージェントBがAのブランチをレビュー。BはAのコードのピアリング・スナップショットから読み、差分を見て、B自身のサンドボックスでテストスイートを走らせ、レビューコメントを投稿します。BにはAのコードへのpush、merge、変更の経路はありませんが、Bのレビューは実装者が与えた要約でなく実際のコードに根ざしています。
  </BulletItem>
  <BulletItem heading="複数サンドボックスにまたがるドキュメント生成">
    ドキュメント生成エージェントが多数のサンドボックスから読み取ってクロスプロジェクトのドキュメントを生成します。それぞれのソースコード（型、関数シグネチャ、READMEファイル）を見て、統合ドキュメントを作ります。どのプロジェクトのデプロイキーも保持せず、どのプロジェクトのデータベースアクセスも持ちません。出力はテキスト、入力はコード、境界はピアリング・プリミティブです。
  </BulletItem>
  <BulletItem heading="フロントエンドがバックエンドの型を参照">
    フロントエンドのサンドボックスがバックエンドのサンドボックスからAPIの型を必要とします。読み取り専用ピアリングがフロントエンドエージェントにバックエンドのTypeScript型、OpenAPIスペック、Protobuf定義への可視性を与え、フロントエンドエージェントにバックエンドのデータベースアクセスやデプロイ権限を与えません。バックエンドが変わったら、スナップショットを更新します。
  </BulletItem>
</BulletList>

形は常に「AはBから文脈を必要とするが、AはBの権限を獲得してはいけない」です。マルチエージェント協働が起こるところならどこでも出てくる形です。ピアリング・プリミティブは、それを安全にするランタイム性質です。

## このプリミティブがやらないこと

率直な限界を。

これはテナント間アクセス用ではありません。ピアリングは同じアカウント内のサンドボックスのためです。アカウント間アクセスは脅威モデルが異なり、ピアリング・プリミティブそのものを超える追加の制御を必要とします。

これはgitの代替ではありません。AとBが共有コードベースで作業しているなら、両方ともピアリング・スナップショットからではなく共有gitリポジトリから作業すべきです。ピアリングは「AがBの作業成果を読む」用、gitは「AとBが同じコードで協働する」用です。

これはBが内側から漏らすことに対しては保護しません。サンドボックスB自体が侵害され、Bのエージェントが承認済みチャネル経由でデータを抜き取っているなら、ピアリング・プリミティブは助けになりません。Bのアクションは依然としてBのアクションです。ピアリングはAをBから保護します。BをB自身の欠陥から保護はしません。

これは自動更新しません。時点指定の意味論は意図的ですが、ユーザーが更新する必要があります。リアルタイムのサンドボックス間状態に依存するワークフローは異なるメカニズム（ライブデータ製品、明示的な付与を伴う共有データベース）を必要とします。

これらはバグではなく、プリミティブが設計上行うことの境界です。他の問題には他のプリミティブが当たります。

## 仕様はどこで読めるか

実装の詳細（厳密なrsyncフラグ、完全な除外リスト、スコープチェックの呼び出し順）は [Ellulドキュメントの Cross-Sandbox Sharing](https://docs.ellul.ai/projects/sharing-projects) にあります。周辺の並列エージェントアーキテクチャについては [/concepts/parallel-agents](/concepts/parallel-agents) ページがより広いパターンを述べます。なぜランタイムが存在するのか（そしてなぜここがこのようなプリミティブを置く正しい場所なのか）については [エージェント・ワークステーションの柱ページ](/concepts/agent-workstation) が標準的な参照先です。

ピアリング・プリミティブは、私たちが形を正しく捉えられたと感じる設計判断の1つです。一般化可能で、どのエージェント・プラットフォームもこれに似たものを持つべきです。「シークレットファイル除外付きrsync＋4層のスコープチェック」という具体は、抽象を扱いやすくするものです。それなしで「エージェント間で読み取りアクセスを共有させよう」とすれば、セキュリティ災害が起こるのを待つだけです。
