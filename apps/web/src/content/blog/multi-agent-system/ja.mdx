マルチエージェントシステムとは、2つ以上の言語モデルエージェントが共同してタスクに取り組む構成のことです。この定義は、役立つほどに短いです。それ以外のほとんどはこの分野で議論の対象です。合意されたアーキテクチャはなく、定番のフレームワークもなく、「より良いツールを持つ単一エージェントよりマルチエージェント構成の方が良かったか」を測るベンチマークもありません。

この記事はビルダー視点の見方です。どのパターンが実用に耐えるか、それぞれどこで失敗するか、本番で安全に動かすためにランタイムが何を提供しなければならないか、を扱います。

この領域に新しい方へ、「マルチエージェント」はソフトウェアパターンです。「[parallel agents](/concepts/parallel-agents)」はランタイム特性で、状態衝突なしに複数のエージェントを同時実行することです。両者はよく混同されます。2026年のマルチエージェントのデモのほとんどは、エージェントを直列に実行しています。真の並列性が必要なのは一部だけです。両方とも有用ですが、同じ問題ではありません。

## 実用に耐える3つのパターン

数百件のマルチエージェントの試みが出荷され、撤回されるのを見てきた結果、3つのアーキテクチャ形が繰り返し現れます。それ以外のほとんどは、このどれかのバリエーションです。

### パターン1:パイプライン

1つのエージェントがあるステップを終えて、明示的に次のエージェントへ引き継ぎます。各エージェントは狭い役割、明確な入力契約、明確な出力契約を持ちます。パイプラインは並行ではなく逐次で、引き継ぎが設計面の中心です。

<CodeTabs>

**スケッチ(Python 擬似コード):**

```python
# A research, write, review pipeline.
research_agent = Agent(role="researcher", tools=[search_web, read_url])
writer_agent   = Agent(role="writer",     tools=[draft_doc])
review_agent   = Agent(role="reviewer",   tools=[lint, fact_check])

brief = research_agent.run(topic="multi-agent systems in 2026")
draft = writer_agent.run(brief=brief)
final = review_agent.run(draft=draft, brief=brief)

return final
```

</CodeTabs>

パイプライン・パターンが効くのは、タスクが境界の明確な段階に分解できるときです。段階が独立でないと失敗します。執筆者がリサーチャーの取りこぼした文脈を必要とする、レビュアーがブリーフに既に焼き込まれた前提に異議を唱えたい、といった場合です。引き継ぎは情報を失います。失われる情報がたまたま重要でない種類の作業に、パイプラインは向いています。

### パターン2:スーパーバイザー

監督役のエージェントが、各ステップでどのサブエージェントを呼ぶかを決めます。スーパーバイザーが計画を保持します。サブエージェントは、スーパーバイザーが呼ぶツールです。スーパーバイザーから見れば「Pythonコーダー」は1つの関数です。Pythonコーダーから見れば、毎回新しい文脈で起動されています。

<CodeTabs>

**スケッチ(Python 擬似コード):**

```python
# A supervisor with three specialists.
specialists = {
  "code":   Agent(role="python-coder",   tools=[run_python, edit_file]),
  "data":   Agent(role="data-analyst",   tools=[query_sql, plot]),
  "search": Agent(role="web-researcher", tools=[search_web, read_url]),
}

supervisor = Agent(
  role="supervisor",
  tools={ name: agent.as_tool() for name, agent in specialists.items() }
)

answer = supervisor.run(
  task="Investigate this customer churn anomaly and propose a fix."
)
```

</CodeTabs>

スーパーバイザー・パターンが映えるのは、タスクの構造が「サブステップごとに正しい専門家を選ぶ」になるときです。リサーチ、コード、デバッグ、要約。失敗するのは、サブエージェントが書き換えている状態についてスーパーバイザーが推論しなければならないときです。スーパーバイザーはサブエージェントの戻り値しか見ないからです。サブエージェントが戻り値に入らなかった有用な中間観測を持っていても、スーパーバイザーはそれを持ちません。

### パターン3:ピア

複数のエージェントが並行に動き、それぞれが自分のツールと目標を持ち、明示的なメッセージか共有(ただし可変なことは稀)のワークスペースで連携します。代表的な版が [parallel agents](/concepts/parallel-agents) パターンです。コーディングエージェント、レビューエージェント、ドキュメント化エージェントが、同じソースツリーに同時に取り組み、互いを読み取り専用でピアします。

<CodeTabs>

**スケッチ(オーケストレーション擬似コード):**

```python
# A coder, a reviewer, and a documenter running concurrently.
# Each has its own workstation. The reviewer and documenter
# read the coder's working tree via a read-only peer mount.

coder      = Workstation(role="coder",       project="payments-api")
reviewer   = Workstation(role="reviewer",    peer_read=[coder])
documenter = Workstation(role="documenter",  peer_read=[coder])

# Run all three concurrently.
results = await asyncio.gather(
  coder.run(task="Add idempotency keys to POST /charges"),
  reviewer.run(task="Watch for SQL injection, missing tests"),
  documenter.run(task="Update the API reference for the new param"),
)
```

</CodeTabs>

ピアは、微妙なバグが最も出やすいパターンです。2つのエージェントが同じファイルに同時に書き込む。あるエージェントが別のエージェントの半分だけ適用された変更を読む。「失われた更新」、つまり2つのエージェントが互いの変更を上書きしてコミットする。修正は規律の徹底ではありません。構造的な対処です。各エージェントに、独自のファイルシステム、独自のプロセスツリー、独自の認証情報を与えます。連携はデフォルトで読み取り専用です。書き込み権限は、リソースごとに1つのエージェントだけに帰属させます。

## それぞれのパターンはどこで失敗するか

各パターンには特有の失敗モードがあります。何が最初に壊れるかを知ることが、出荷できるマルチエージェントシステムと、四半期で剥がされるそれとの違いになります。

<Callout variant="warn" title="パイプライン:引き継ぎでの情報損失">
最も多いバグは「次の段階に必要なものが揃っていなかった」というものです。ブリーフが短すぎた。ドラフトが制約を見落としていた。レビューが、ある決定の理由を判断できなかった。修正は契約設計です。この段階が何を生成し、次の段階が何を消費するかを明示する必要があります。「エージェントが何とかするだろう」は契約ではありません。
</Callout>

<Callout variant="warn" title="スーパーバイザー:壊れやすい分解">
スーパーバイザーは推論の単一点です。計画が間違っていれば、サブエージェントは高い能力で間違った計画を実行します。さらに悪いことに、スーパーバイザーは時にループを起こし、別の結果を待って同じサブエージェントを微妙に異なる呼び方で何度も呼び、コンテキストとトークンを焼き尽くします。監督の深さに上限を設け(タスクごとの最大ステップ数)、トレースの中でループのシグネチャを監視してください。
</Callout>

<Callout variant="warn" title="ピア:状態の破損と暴走するコスト">
ピアの並列性は状態を増やすと同時に、破損の可能性も増やします。同じブランチ上の2人のコーディングエージェントが、初期のピア構成のほとんどを潰す失敗モードです。コストは並行エージェント数とともにスケールし、上限のないピア並列性(3人ではなく8人)は、艦隊が生成する速度では人間に読み切れない出力を作ります。艦隊の出力は読まれません。支出は実在します。
</Callout>

## ランタイムが提供しなければならないもの

フレームワーク選び(LangGraph、CrewAI、AutoGen、自作)は、フレームワークの下にあるランタイム特性ほど重要ではありません。重要なのは3つで、ほとんどのデモは3つすべてを飛ばします。デモはノートPCで一度動けば良いからです。

<NumberedList>
  <NumberedItem heading="状態の隔離">
    各エージェントが、独自のファイルシステム、プロセスツリー、認証情報、ネットワーク名前空間を持つこと。同じノートPC上で2つのエージェントが `node_modules` や `.git/index.lock` を奪い合うのは、どんなオーケストレーションフレームワークでも覆い隠せない種類の失敗です。修正はフレームワークの下、ランタイムにあります。
  </NumberedItem>
  <NumberedItem heading="明示的な引き継ぎ">
    エージェント間の共有可変状態は地雷です。規律ある版は読み取り専用ピアです。エージェント A は、エージェント B に A のワークスペースのフィルタ付きの読み取り専用スナップショットを渡します。B はそれに対して解析、要約、レビュー作成を行えます。B は A のツリーを変更できません。書き込み権限はリソースごとにスコープされたままです。
  </NumberedItem>
  <NumberedItem heading="特権アクションのゲート">
    艦隊のどのエージェントも、人間の承認なしに本番にプッシュしません。どのエージェントも、passkey のタップなしに実アカウントに対して `terraform apply` を実行しません。ゲートはランタイムの境界、エージェントプロセスの外側に置きます。だから、艦隊内の侵害されたエージェントもこれを迂回できません。マルチエージェントでは失敗の表面がエージェント数に比例して大きくなるので、ここが特に重要です。
  </NumberedItem>
</NumberedList>

実用で持ちこたえてきたパターンは、それぞれが自分の[エージェントワークステーション](/concepts/agent-workstation)を持ち、読み取り専用ピアと、特権アクションへのサーバー側ゲートを備えた、2人または3人のエージェント構成です。フレームワークのデモに比べると地味です。それでも、作業が現実のものであるときに動くのは、こちらです。

## フレームワーク:どれを選ぶか

LangGraph、CrewAI、AutoGen は2026年に理解する価値のある3つのフレームワークで、おおよそその順番で採用されています。それぞれメインの比喩が違います。LangGraph はグラフ明示型で、状態機械を描き、それを実行します。CrewAI は役割明示型で、ペルソナ(リサーチャー、ライター、レビュアー)を定義し、それぞれにツールと目標を与えると、フレームワークが会話を編成します。AutoGen は会話明示型で、エージェント同士が(そして人間とも)フレームワークが管理する転写の中で会話します。

タスクに合う比喩で選んでください。制御フローが設計の中心なら LangGraph。役割の分解が設計の中心なら CrewAI。反復的な往復が設計の中心なら AutoGen。ベンチマークで選ばないでください。あなたのコードベースの中でコードを短くしてくれる抽象で選んでください。

選んだフレームワークは荷重を支える部分ではありません。その下のランタイム特性が支えます。隔離されたワークステーションと passkey ゲートを持つ2エージェントの CrewAI 構成は、ノートPC上で認証情報を共有する8エージェントの LangGraph 艦隊に毎回勝ちます。

## マルチエージェントが間違った答えになるとき

「マルチエージェント」問題のほとんどは、より良いツールを持った単一エージェント問題です。1つの機能を書く、レビューする、デプロイする、監視する、ドキュメント化するために5エージェントの構成を作っているなら、5つのツールを持つ単一エージェントの方が良くないかを問うてください。多くの場合、答えはイエスです。引き継ぎが減り、プロンプトのオーバーヘッドが減り、計画監督ループがなくなります。

マルチエージェントの根拠が強くなるのは、エージェントが本質的に異なる目標を持つとき(コーダーとレビュアーが代表例で、彼らは反対の立場を取るべき)、エージェントが異なるツールやモデルを必要とするとき(トリアージには安いモデル、執筆には高価なモデル)、並行性が勝つとき(あるエージェントがバグを修正している間に別のエージェントがリグレッションスイートを走らせる)です。どれも当てはまらなければ、答えは単一エージェントです。
