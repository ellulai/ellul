エージェントランタイムの領域では、2つのアーキテクチャが主流になっています。エフェメラル・サンドボックスはセッションごとに立ち上がり、エージェントのコードを実行し、終わると消滅します。永続ワークステーションはセッションをまたいで存在し続け、インストール済みの依存、エージェントの状態、温まったコンテキストはすべて利用の合間も生き残ります。両者は異なる問題を解き、異なる失敗の仕方をし、その中間にあるハイブリッドモデルが、実用的な答えとして次第に主流になりつつあります。

この記事は比較エッセイです。両者を定義し、それぞれについて具体例を辿り、各カテゴリの製品を挙げ、最後に静かにデフォルトとなりつつあるハイブリッド・パターンで締めます。判断は「どちらが優れているか」よりも、「実際にやっている作業に合っているか」の問題です。

## 2つのモデルを定義する

エフェメラル・サンドボックスとは、コンテナ、microVM、またはプロセス分離された環境で、1つのエージェントタスクの間だけ存在するものです。寿命は数百ミリ秒から数分、ときに最大1時間。状態はセッション終了後に何も残りません。コールドスタートは積極的に最適化され、多くは1秒未満です。例:e2b、Modal、Cloudflare Workers(構成によっては)、AWS Lambda(拡張使用時)。メンタルモデルは「毎回まっさらな実行環境」です。

永続ワークステーションは、多くのエージェントセッションをまたいで存在する長寿命の環境(VM、コンテナ、または専用ホスト)です。寿命は日単位から月単位。状態は、ファイルシステム、プロセス、インストール済みパッケージ、設定、エージェントの文脈すべてが残ります。コールドスタートは、初回プロビジョニングで数分、スリープからの復帰では数秒から数分です。例:Ellul の[エージェントワークステーション](/concepts/agent-workstation)、Daytona ワークスペース、GitHub Codespaces(保持時)、セルフホストの開発 VM。メンタルモデルは「エージェントが住むためのコンピュータ」です。

これらは別の帽子をかぶった同じ製品ではありません。性能、コスト、運用上の特性は大きく分岐します。間違った方を選ぶと、ワークフローと1年戦うことになります。

## エフェメラルが勝つとき

エフェメラル・サンドボックスは、作業が次の特性を持つときに正解になります。短時間(1秒未満から数分)、ステートレス(結果は戻り値で、永続的な変更ではない)、スコープが限定(1つのツール呼び出し、1つのコード実行、1つのデータ変換)、高いボリューム(独立したリクエストが多数あり、それぞれに隔離が必要)、コスト感度が高い(アイドル中のワークスペース時間に支払うのが支配的になる)。

具体例。

<BulletList>
  <BulletItem heading="LLM のツール使用によるコード実行">
    Anthropic の Claude や OpenAI のモデルが「この Python を実行する」ツールを呼ぶ。コードを評価する隔離された環境が必要です。e2b の API はまさにこれ向けに作られています。呼び出しごとにまっさらなサンドボックス、コードが走り、結果が返り、サンドボックスは消える。トレードオフの形については[e2b 比較](/vs/e2b)を参照してください。
  </BulletItem>
  <BulletItem heading="外部ソースから来る信頼できないコード">
    ユーザーが評価のためにコードを投稿できるプラットフォーム。競技プログラミングの審判、AI 評価パイプライン、サンドボックス型のプラグインシステム。各投稿は独立で信頼できません。エフェメラル隔離が正しいパターンです。
  </BulletItem>
  <BulletItem heading="データ変換パイプライン">
    モデルがスクリプトを生成し、そのスクリプトを CSV に対して実行し、結果が変換済み CSV になる。Modal や Cloudflare のコンピュート API のようなワークフロー編成ツールがよく合います。
  </BulletItem>
  <BulletItem heading="ブラウザベースの vibe coding">
    ブラウザサンドボックスは、編集体験の一部としてユーザーコードを実行します。StackBlitz の WebContainers が [Bolt](/vs/bolt) の基盤です。Replit のホットリロードランタイムが [Replit Agent](/vs/replit) を支えます。必然的にエフェメラル(ブラウザのタブはいつでも閉じられる)ですが、パターンは作業に合っています。短命でデモ規模、リセット可能。
  </BulletItem>
</BulletList>

エフェメラルが得意なこと。コールドスタートのコストは、無限の将来の呼び出しに対して償却されます。実際は将来の呼び出しはなく、次の呼び出しがあるだけで、それもまた新規です。コストは完全に従量制。セキュリティ境界は自然に短命で、攻撃者の滞留時間を制限します。

エフェメラルが苦手なこと。永続的な状態に依存する作業すべて。インストール済み依存、学習した文脈、進行中のプロジェクト状態を、毎セッション再取得しなければなりません。5分のタスクなら問題ありません。5時間のタスクでは、コールドスタートの累積コストが支配的になります。

## 永続が勝つとき

永続ワークステーションは、作業が長時間(数分から数日、ときに数週間)、ステートフル(インストール済み依存、設定、エージェントの文脈、進行中のファイルがすべて重要)、セッションをまたいで一貫(エージェントの「朝の自分」が「夜の自分」の状態から続く)、マルチセッション(同じプロジェクトに何度も触れて、その間も状態が生きる)、長時間動作するツールを使う(MCP サーバー、ファイルウォッチャー、language server、開発サーバーがすべて立ち上がったままで恩恵を受ける)、というときに正解になります。

具体例。

<BulletList>
  <BulletItem heading="コードベースを保守するコーディングエージェント">
    エージェントはディスク上にプロジェクトを持ち、`node_modules` がインストール済みで、テストスイートはキャッシュ済み、開発サーバーは温まっています。新しいタスクが来ると、エージェントは前回の状態から続けます。セッションごとにコールドスタートすれば、毎朝依存を再インストールし、毎朝キャッシュを温め直し、毎朝プロジェクトの規約を読み直すことになります。永続ランタイムはウォームアップコストを多数のセッションにわたって償却します。
  </BulletItem>
  <BulletItem heading="夜通しの実行">
    長時間の[Claude Code を一晩動かす実行](/blog/run-claude-code-overnight)では、ユーザーが寝ている間もランタイムが動き続ける必要があります。エフェメラル・サンドボックスは定義上これができません。セッションが命の単位です。永続ワークステーションが自然な選択肢です。
  </BulletItem>
  <BulletItem heading="ピアを伴う parallel agents">
    [parallel agents 構成](/concepts/parallel-agents)(あるエージェントがコードを書き、別のエージェントがレビューし、3人目がドキュメント化する)は、共有ファイルシステムのスナップショットとエージェント間の読み取り専用ピアに依存します。両方とも、その下のワークスペースが永続している方が容易です。エフェメラルなピアは、反復のたびに状態を再同期しなければなりません。
  </BulletItem>
  <BulletItem heading="MCP サーバーと開発者ツール">
    [MCP](/glossary/mcp) サーバーは長寿命に設計されています。コードベースをインデックスし、外部システムへの接続を保持し、結果をキャッシュします。セッションごとに立ち上げると、インデックスとキャッシュが失われます。MCP に正しいモデルは永続ランタイムで、サーバーがエージェントと並んで立ち上がり続けることです。
  </BulletItem>
</BulletList>

永続が得意なこと。温まった文脈、インストール済み依存、マルチセッションの連続性、中断を越えた持続性。累積効果として、新しいセッションのエージェントの最初のアクションがすぐに生産的になり、最初の1分を自分の以前の状態を再発見することに費やさなくて済みます。

永続が苦手なこと。アイドル中のコスト。24/7存在するワークスペースは、エージェントが4時間しか活動していなくても24/7分支払います。時間あたりコストはエフェメラルより低いですが、何も起きていないときにゼロまで落とす方法はありません。

## 具体的な比較

同じタスクを両アーキテクチャで、正直に勘定する。

タスク:「このモノレポの全マイナー依存をアップグレードし、それぞれについてテストスイートを実行し、パッケージごとに PR を開く。」

エフェメラル・サンドボックス上では、サンドボックスが立ち上がり、リポジトリをクローン(コールド)、`npm install` を実行(コールド、数分)、1パッケージをアップグレード、そのパッケージのテストスイートだけを実行、PR を開いて、終了。次のパッケージのために新しいサンドボックスが立ち上がります。新規クローン、新規インストール、など。50パッケージなら、50回のコールドインストールに支払います。ジョブはおおむね N×(クローン+インストール+実行) 時間で動きます。並列化は可能ですが高くつきます。

永続ワークステーション上では、リポジトリはすでにクローン済み。`node_modules` はすでにインストール済み。エージェントはパッケージ1をアップグレードし、関連テストを実行し、PR を開きます。パッケージ2に移る:`node_modules` は熱く、変更されたパッケージだけ再インストールが必要です。50パッケージで、インストールコストは全パッケージにわたって償却されます。ジョブはおおむね クローン+インストール+N×実行 時間で動きます。

この特定のタスクでは、永続がコストと時間で勝ちます。「このコードスニペットを評価する」ではこの計算は逆転します。そこではエフェメラルが唯一まともなパターンです。

## 製品マップ

ランタイムの全体像を2つのアーキテクチャに対応付けます。

純エフェメラル。e2b は API としてのサンドボックス。タイトなコールドスタート、ツール使用向け設計。[/vs/e2b](/vs/e2b)。Modal は ML ワークロード向けの function-as-a-service。コールドスタートが速く、バッチに合うエルゴノミクス。Cloudflare Workers と Lambda は汎用のサーバーレスコンピュートで、エージェント特化度は低めです。

純永続。Ellul はエージェントごとに1つのエージェントワークステーションを提供します。[/concepts/agent-workstation](/concepts/agent-workstation)。セルフホストの Linux ボックスは元祖の永続ワークステーションで、実用的かつ過小評価されています。

ハイブリッド(ウォームプール+休止と再開)。GitHub Codespaces はワークスペースを永続化し、アイドル時にサスペンドし、アクセス時に再開します。[/vs/codespaces](/vs/codespaces)。Daytona はワークスペースを永続化し、休止に対応します。オープンソース。[/vs/daytona](/vs/daytona)。Sprites はエージェント・ランタイム領域での新規参入で、ハイブリッドなライフサイクルを持ちます。[/vs/sprites](/vs/sprites)。

ハイブリッドのカテゴリが最も急速に成長しています。次節がその理由です。

## ハイブリッド・パターン(ウォームプール+休止と再開)

純エフェメラル/純永続の二項対立は、現実の負荷の下では持ちこたえません。実ワークロードは短いツール呼び出しと長いセッションが混在します。純エフェメラルは長いタスクでコールドスタート税を払います。純永続は短いタスクでアイドル税を払います。自然な答えは、適応するランタイムです。

現れているパターン:ワークスペースの状態はディスク上に永続化され(ファイルシステム、インストール済み依存、エージェントの文脈はすべて利用の合間も残る)、アイドル時にコンピュートをサスペンドし(エージェントが活動していないとき、ワークスペースの CPU はゼロに落ち、ランタイムはプロセスを休止し、メモリをスナップショットし、コンピュートを解放する)、再開は速い(活動が戻ると、ランタイムはスナップショットから数分ではなく数秒で復元する)。

トレードオフ。

ウォームプールのオーバーヘッド。即応のために、少数のワークスペースをスタンバイで温めておきます。これは容量の数パーセントですが、システムが完全にコールドにならないことを意味します。

スナップショット/再開のコスト。サスペンドと再開には実コストがあります。一般にサイクルあたり数百ミリ秒から数秒です。攻撃的な休止ポリシーはこれを頻繁に踏み、対話的な感触をはっきり劣化させ得ます。

複雑さ。ランタイムは状態が増えます(active、suspending、suspended、resuming、terminated)。遷移のバグは、丁寧に扱わないとユーザーから見える不安定さの原因になります。

ほとんどのエージェント・ワークロードでは、ハイブリッド・パターンが実際に欲しいものです。純エフェメラルは狭いが重要なスライスに合います(ツール使用、信頼できないコード実行、短い変換)。純永続は、即時再開がアイドル・コストよりも重要なケースに合います(対話的な vibe coding、常時稼働のエージェント)。

## Ellul はこのトレードオフにどう向き合うか

簡潔な正直開示。私たちは永続ワークステーションの会社です。永続をデフォルトに選んだのは、私たちが最適化対象とするワークロード、つまり実プロジェクトに数時間から数日かけて取り組むコーディングエージェントが、温まった文脈から圧倒的に恩恵を受けるからです。アイドル・コストの削減を取り込むため、2026年後半に休止機能を追加します。永続のデフォルトは変わりません。

永続性に依存して提供している機能。

インストール済み依存は再起動を越えて生き残ります。エージェントの `~/.openclaw/`、`~/.claude/`、`~/.codex/` の設定と履歴はセッションをまたいで残ります。MCP サーバーはエージェントセッションの間も立ち上がったままです。開発サーバーはあなたが眠っている間も走らせ続けられます。[parallel agents のピア](/concepts/parallel-agents)は、別のワークステーションのファイルシステムのスナップショットから読み取りますが、これは両ワークステーションが永続的なファイルシステムを持つ場合にのみ意味があります。[Sovereign Shield](/glossary/sovereign-shield) は長寿命の OAuth トークンとセッション鍵を保持しますが、それらをセッションごとにローテートすると UX が破綻します。

ワークロードが「この Python スニペットを評価する」なら、これらは何も要りません。e2b か Modal を使うべきです。ワークロードが「保守すべきプロジェクトがある限り、エージェントが私のプロジェクトを保守し続ける」なら、永続性は構造的で、ワークステーション・パターンが合います。

## 判断ツリー

作業はセッションを越えて状態が生き残る必要があるか。いいえならエフェメラル・サンドボックス。e2b か Modal を選びます。はいなら永続またはハイブリッド。

作業の大半は長セッションで、たまに空きがあるか。長セッション中心で常に活動的なら永続。Ellul かセルフホストの Linux ボックスを選びます。長セッションだがアイドル時間が大きいならハイブリッド。Codespaces、Daytona を選ぶか、Ellul の休止機能の展開を待ちます。

アイドル中の時間あたりコストが致命的か。はいならハイブリッドが必須。永続では望む以上に高くつきます。いいえなら永続で問題ありません。シンプルさが価値になります。

すべてを楽にする形は、ランタイムをワークロードに合わせることです。永続的な作業を純エフェメラル・ランタイムにやらせて戦わない。エフェメラルな作業のために永続ランタイムを払わない。どちらの極端も合わなければハイブリッドを検討する。
