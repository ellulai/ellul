# Deploy protection

Deploying customer code (writing to Caddy site blocks, reloading Caddy, restarting preview servers) is gated by user approval and protected by Caddy directory isolation.

## The threat

The agent has access to user code. If the agent could:

1. Add a Caddy site block claiming a customer's domain, OR
2. Reload Caddy to apply a malicious config,

it could redirect traffic, host phishing pages, or expose backend services.

## Defense layers

### 1. Deploy gate token

The agent must hold a `deploy` gate token (issued via user-approved gate request). Without it, Shield's deploy endpoints reject.

### 2. Caddy directory isolation

```
/etc/caddy                       caddy:caddy 2770 (SGID)
/etc/caddy/sites-enabled/        caddy:caddy 2770
/etc/caddy/app-routes.d/         caddy:caddy 2770
/run/caddy                       caddy:caddy 2770 (SGID)
```

The agent (`dev`) is **NOT** in `caddy` group. POSIX denies write.

Shield-runner IS in `caddy` (via `SupplementaryGroups`) and CAN write. But Shield won't write a site block without a valid gate.

### 3. Admin socket (not TCP)

Caddy's admin API is on Unix socket `/run/caddy/admin.sock` (`caddy:caddy 2770`), NOT on TCP `localhost:2019`.

If it were TCP, anything on the host could `curl http://127.0.0.1:2019/load -d @config.json` and reload Caddy. With Unix socket + group permissions:

- Only `caddy` user (Caddy itself) and group members can connect.
- Shield-runner is in `caddy` (supplementary), so Shield can reload.
- Agent is not, cannot.

Shield invokes:

```bash
sudo /usr/bin/caddy reload --address unix//run/caddy/admin.sock
```

with sudo entry restricted to this exact command. The unix socket path is hardcoded in `caddy-gen` at `caddy-gen/caddyfile.ts:CADDY_ADMIN_SOCK`.

### 4. Sudoers narrow

Shield-runner's sudoers entries (and only theirs):

```
shield-runner ALL=(root) NOPASSWD: /usr/local/bin/ellul-caddy-gen
shield-runner ALL=(root) NOPASSWD: /usr/bin/caddy reload --address unix//run/caddy/admin.sock
shield-runner ALL=(caddy) NOPASSWD: /bin/chown caddy:caddy /etc/caddy/Caddyfile
```

Agent has no equivalent. Even if agent invokes `sudo /usr/bin/caddy reload`, sudoers denies (rule is for shield-runner only).

### 5. Caddyfile validation before reload

Shield always:

```bash
sudo /usr/local/bin/ellul-caddy-gen ... > /etc/caddy/Caddyfile.new
sudo caddy validate --config /etc/caddy/Caddyfile.new
sudo mv /etc/caddy/Caddyfile.new /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Validation catches syntax errors before swap. A bad config doesn't break the live service.

### 6. Per-project app routes file

Customer apps deployed via the `deploy` flow get a per-app file:

```
/etc/caddy/sites-enabled/sbx-abc1234.caddy
```

Shield writes this file when the deploy gate is approved and includes appropriate auth/routing for the app. The file is not directly modifiable by the agent.

## How a deploy actually works

```
User: clicks "Deploy" in dashboard
  ↓
API → Shield: POST /_auth/gates/request { gate: "deploy", appId: "sbx-abc1234" }
  ↓
Dashboard popup: "Deploy this app to your domain?"
  ↓
User approves
  ↓
Shield issues deploy gate token, marks request approved
  ↓
Agent (or a workflow script) calls Shield POST /_internal/deploy with token + manifest
  ↓
Shield:
  1. Verify gate token + LUKS-mounted check
  2. Run app-specific build commands (in namespace)
  3. Generate site block via caddy-gen for this app
  4. sudo caddy validate
  5. atomic mv to /etc/caddy/sites-enabled/sbx-abc1234.caddy
  6. sudo systemctl reload caddy
  7. Audit log: 'deploy.success'
  ↓
Caddy now serves <user-app-domain> from the new app port
```

## What the agent CAN'T do

- Write directly to `/etc/caddy/sites-enabled/` (group denies).
- Connect to admin socket (group denies).
- `sudo caddy` — sudo entry is for shield-runner only.
- Change global Caddyfile (requires Shield's caddy-gen path).
- Reload Caddy (no admin socket access).
- Add itself to caddy group (`usermod` not in agent's sudo allowlist).

## What the agent CAN do

- Request the deploy gate.
- After approval, ask Shield to deploy via internal API (which Shield then performs as shield-runner).

The agent is the requester; Shield is the actor. The gate is the user's approval.

## Sites-enabled vs Caddyfile imports

The base `/etc/caddy/Caddyfile` is generated by `caddy-gen` and imports `sites-enabled/*.caddy`:

```
import /etc/caddy/sites-enabled/*.caddy
```

So adding/removing a site block is an atomic-ish operation: write the file (atomic via `mv -Tf`), then reload Caddy (which re-parses imports). No restart needed.

## Why not let the agent reload Caddy directly?

A common shortcut: "the agent runs `caddy reload`; the admin socket is local."

Rejected because:

- Allows trivial DoS (the agent reloads with bad config, Caddy keeps last-known-good but logs flood).
- Allows trivial config injection (the agent edits the file before reload).
- Bypasses user approval entirely.

The deploy-gate-mediated path is slower but verifiable.
